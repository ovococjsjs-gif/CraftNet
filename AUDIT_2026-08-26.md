# CraftNet — независимое техническое и геймдизайнерское ревью

Дата: 2026-08-26  
Проверенная ветка/ревизия: `arena/01a03ad1-craftnet`, база `b68fd837bb7281c6e7c71e09e85f8f9103141b68`

## 1. Краткий вывод

Субъективная оценка автора совпадает с состоянием репозитория: это не небольшая
полировка, а кандидат на переработку основных контуров мода.

Главные проблемы:

1. **Генерация зданий имеет два пути, но ни один нельзя считать надёжным.**
   Jigsaw-путь фактически неработоспособен: шаблоны не содержат ни одного
   `minecraft:jigsaw`. Программный fallback хрупок, повторяет те же кандидаты,
   может записать успех без проверки результата и навсегда помечает деревню как
   «сдались» после 30 повторов.
2. **Операции с предметами теряют Data Components.** Казино, ПВЗ и барахолка
   агрегируют предметы только по registry id. Зачарования, прочность, имя,
   содержимое шалкера/бандла и другие компоненты игнорируются. Это одновременно
   риск потери вещей и эксплойт бесплатного ремонта через «положить → вернуть».
3. **Антиэксплойт работ обходится.** Тег выданных материалов не обязан переходить
   в результат обычного крафта, штраф списывается только в пределах текущего
   баланса, а груз при сдаче проверяется по типу предмета, не по job-тегу.
4. **Экономика проверена против собственного упрощённого набора предположений,
   а не против реальной игры.** Не учтены Fortune, Data Components, фермы,
   переплавка, фактические рецепты и время выполнения. Есть прямые перекосы и
   ожидаемый положительный арбитраж на покупных рудах.
5. **UI — фиксированная пиксельная раскладка, а не адаптивный интерфейс.**
   `PhoneScreen` — монолит на 1735 строк с размером 300×240, самодельными полями
   ввода и сотнями жёстко прошитых русских строк. На малой scaled resolution
   экран уходит за границы окна.
6. **Апгрейдер показывает театральную рулетку после уже принятого результата.**
   Сервер сразу сжигает ставку, выдаёт приз/сообщение/звук, а клиент лишь затем
   запускает трёхсекундную анимацию и второй звук. Излишняя ставка выше cap
   сгорает без пользы.
7. **Зелёный CI означает только компиляцию.** Java/GameTest/integration-тестов
   нет; Python-аудиты в Gradle/CI не подключены. Один из аудитов даже парсит
   закомментированные `put(...)` как реальные цены.

### Приоритеты

| Уровень | Смысл | Количество комплексов |
|---|---|---:|
| P0 | потеря предметов, дюпы/эксплойты, сломанный основной цикл | 3 |
| P1 | крупные функциональные, экономические и UX-дефекты | 10 |
| P2 | архитектура, локализация, документация, качество поддержки | 7 |

До исправления P0 мод **не стоит публиковать как production-ready**.

# 3. P0 — блокирующие дефекты

## P0.1. Jigsaw-инъекция зданий мертва по конструкции

**Код:**

- `VillageStructureInjector.java:85-87` добавляет NBT как jigsaw pool element.
- `tools/gen_structures.py:82-101` содержит всю палитру шаблонов —
  `minecraft:jigsaw` в ней отсутствует.
- В сгенерированных NBT также нет jigsaw-блоков и connector NBT.

Элемент пула домов должен иметь jigsaw-коннектор, которым он стыкуется с
коннектором дороги/улицы. Простая коробка без коннектора не может быть выбрана и
пристыкована как дом. Вес 5/8 этого не исправляет.

**Следствие:** заявленная в README «инъекция в пулы» не является рабочим резервным
механизмом. Если программное размещение не сработало, зданий действительно нет.

**Что делать:**

- Пересобрать структуры в Structure Block/Jigsaw-совместимом формате.
- Добавить входной `minecraft:jigsaw` с корректными `name`, `target`, `pool`,
  `final_state`, ориентацией и projection.
- Сделать отдельные biome-specific template pools/processors.
- Добавить GameTest: сгенерировать по деревне каждого типа и assert-ить наличие
  хотя бы одной станции/NPC либо явный программный fallback.

## P0.2. Казино, ПВЗ и барахолка уничтожают компоненты ItemStack

### Казино

- `CasinoManager.java:122-155` снимает предметы по одному `Item` и хранит только
  `{id,count}`.
- `CasinoManager.java:163-167` возвращает `new ItemStack(item, count)`.

Повреждённый зачарованный предмет превращается при возврате в новый дефолтный:
исчезают зачарования/имя, но одновременно полностью восстанавливается прочность.
Это и data loss, и бесплатный repair exploit.

### Барахолка

- `MarketManager.java:104-114` также снимает по `Item`, а в лот записывает новый
  дефолтный `ItemStack`.
- Отмена лота возвращает уже эту дефолтную копию (`MarketManager.java:225-233`).

### ПВЗ

- `ServerActions.java:959-984` агрегирует инвентарь по registry id.
- `ServerActions.java:455-466` продаёт по `Item`, не по конкретному стеку.

Если в инвентаре два меча с разными чарами/прочностью, UI показывает одну строку,
а сервер удаляет стаки в порядке слотов. Игрок не контролирует, какой меч уйдёт.
Для заполненного шалкера последствия хуже: содержимое может исчезнуть полностью.

**Что делать:**

- Никогда не представлять пользовательскую вещь парой `itemId + count`.
- Хранить и передавать точный `ItemStack` через codec, включая components.
- В UI показывать отдельные строки для component-distinct стаков.
- Для продажи серверу ввести явную политику: запрещать контейнеры/кастомные
  компоненты либо оценивать их отдельно; нельзя молча нормализовать вещь.
- Для казино использовать серверный escrow точных стеков и возвращать именно их.
- Написать тесты на damage, enchantments, custom name, shulker contents,
  potions/maps/books и job-tag.

## P0.3. Эксплойты рабочих материалов и груза

### Крафт снимает защиту

`JOB_TAG` стоит на выданных ингредиентах (`JobManager.java:381-388`), но обычные
ванильные рецепты не обязаны переносить произвольный компонент ингредиента в
результат. Результат становится обычным продаваемым предметом.

При отмене считается недостача tagged-ингредиентов (`JobManager.java:619-630`),
но штраф реально списывается только до нулевого баланса
(`JobManager.java:647-650`). Долга нет.

Практический обход:

1. иметь 0 CR;
2. принять заказ и получить материалы;
3. скрафтить untagged-результат;
4. отправить его на отложенную продажу в ПВЗ;
5. отменить смену — списать нечего;
6. дождаться выплаты.

### Груз можно подменить

- Сдача проверяет любой `cargo_crate`/`food_box`, не owner/job tag:
  `JobManager.java:572-578`.
- Ящик имеет обычный рецепт: `data/craftnet/recipe/cargo_crate.json`.
- Успешное завершение не конфискует оставшийся tagged-груз.
- `cargo_crate` — обычный Block с обычным loot table; при размещении/разрушении
  ItemStack component не сохраняется, поэтому tagged-ящик можно отмыть.

**Что делать:**

- У каждой смены должен быть случайный server-side `jobNonce`.
- Сдавать можно только stack с `owner + jobNonce + cargoType`.
- Job-cargo лучше сделать непоставляемым отдельным Item либо BlockEntity,
  сохраняющим и проверяющим компонент.
- Успешное завершение и отмена обязаны удалять все exact-tagged остатки.
- Для крафт-заказов нужен recipe/output hook или отдельный рабочий верстак,
  переносящий job provenance в результат.
- Ввести настоящий debt/escrow или не выдавать ликвидные материалы авансом.
- Добавить adversarial GameTests: drop/trade/place/break/craft/sell/cancel/logout.

# 4. P1 — крупные функциональные проблемы

## P1.1. Программный fallback зданий хрупок и плохо восстанавливается

Проблемы одновременно:

1. RNG каждый вызов получает один и тот же seed от координат
   (`VillageManager.java:353`). Номер повтора `btry` не участвует. Если площадки
   не подходят, 30 повторов в основном проверяют те же места.
2. Возврат `StructureTemplate.place(...)` в `VillageManager.java:387` не
   проверяется; сразу после вызова ставится бит успеха (`:388-390`).
3. После 30 повторов ставится `bld=2` (`:271-273`). Любой будущий rescan упирается
   в ранний return при `bld != 0` (`:346-347`). Команды reset/retry нет.
4. Точки `.` в генераторе означают «не записывать блок»
   (`gen_structures.py:82-84, 110-114`), поэтому шаблон не очищает воздух внутри:
   трава, листья и существующие блоки остаются в комнатах.
5. Проверяются только девять высот, но фундамент не заполняется
   (`VillageManager.java:428-445`). При разрешённом перепаде в два блока часть
   пола может висеть.
6. Постройки автоматически вторгаются в существующий мир/базы без конфига и
   защиты от чужих блоков.

**Рекомендуемая замена:** очередь `VillageBuildTask` с сохранёнными причинами
ошибки, изменяемым seed на попытку, chunk tickets, bounding-box collision check,
проверкой boolean-результата, foundation/terrain processor и админскими
`status`, `retry`, `reset`, `locate`.

## P1.2. Ручная вышка создаёт точку доставки без ПВЗ

`registerManualSite` создаёт запись, похожую на деревню
(`VillageManager.java:546-560`). `signalFor` учитывает её наравне с деревнями
(`:139-151`). Магазин назначает заказ координатам обслуживающей записи
(`ServerActions.java:304-311`).

Но ручная антенна не создаёт ПВЗ. Забрать заказ можно только действием экрана
ПВЗ, находясь ещё и в пределах 96 блоков от адреса (`OrderManager.java:254-287`).
В результате собственная вышка может дать связь, принять деньги и отправить
покупку в фактически недоступную точку.

**Исправление:** разделить `CellSite` и `DeliveryHub`. Сигнал выбирается по
вышкам, доставка — только по ближайшему валидному hub/PVZ; при отсутствии ПВЗ
покупка должна быть заблокирована до списания.

## P1.3. Состояние не учитывает dimension

Почти все менеджеры хранят state в overworld, что нормально для глобальной
экономики, но координатные записи не содержат dimension id.

- `signalFor` сравнивает x/z игрока с overworld-деревнями без проверки мира.
- Станция в Nether с совпадающими координатами может пройти координатные
  проверки.
- `OrderManager.claim` проверяет только x/z (`OrderManager.java:270-272`).
- `growTower` всегда изменяет `server.getOverworld()`
  (`VillageManager.java:658-664`), даже если ядро открыто в другом мире.
- GPS может совместить карту текущего dimension с overworld-метками деревень.

Нужен `RegistryKey<World>` во всех site/station/order/job-target записях и во
всех distance checks.

## P1.4. Сервер доверяет названию экрана из пакета

`ServerActions.handle` выбирает handler по `payload.screen()`
(`ServerActions.java:130-168`), но не проверяет, что он равен `OPEN.screen`.
`nearStation` проверяет лишь расстояние до сохранённого BlockPos (`:81-85`), а
не dimension, существование блока и тип станции.

После открытия ПВЗ модифицированный клиент может отправить `screen=bank` или
`screen=job:factory`: координатная проверка пройдёт около ПВЗ. Роли зданий
становятся условностью.

Нужно маршрутизировать исключительно по server-side `OpenCtx`, хранить
`dimension + station kind + position`, повторно проверять блок/сущность и
отклонять packet screen/action, отсутствующие в allowlist данного контекста.

## P1.5. `/craftnet reload` показывает и применяет разные цены

Каталог кешируется навсегда в `ServerActions.SHOP_CACHE`
(`ServerActions.java:775-800`). Команда reload перечитывает prices, но кеш не
сбрасывает (`AdminCommands.java:126-132`).

После reload:

- UI продолжает показывать старые buy/sell;
- реальная покупка считает новую цену через `PriceManager`;
- шанс выбранной цели казино остаётся рассчитан клиентом по старой цене.

Это прямое нарушение transactional UX. Нужна price/config revision, атомарный
immutable snapshot, инвалидация каталогов и принудительный sync открытых экранов.

## P1.6. Большая часть конфига не reloadable вопреки документации

Значения захватываются в `static final` при загрузке классов:

- доставка/TTL — `OrderManager.java:33-37`;
- комиссия/TTL/лимиты рынка — `MarketManager.java:35-39`;
- interest — `MoneyManager.java:27-29`;
- лимиты казино — `CasinoManager.java:45-47`;
- скидка вышки — `VillageManager.java:68`.

`/craftnet reload` меняет объект config, но перечисленные константы остаются
старыми до рестарта. UI при этом содержит ещё и hardcoded `5%`, `0.15%`, `50 CR`,
`64`, `3 дня`.

## P1.7. Прайс содержит реальные игровые арбитражи и плохие стимулы

### Fortune-arbitrage

- diamond = 140, sell = 95;
- diamond ore = 170;
- средний Fortune III output приблизительно 2.2 diamond;
- ожидаемая продажа: `2.2 × 95 ≈ 209 CR` при покупке руды за 170.

Ожидаемая маржа около **+39 CR с блока** до учёта короткого времени/прочности.
Для deepslate diamond ore остаётся около +9; похожая проблема есть у emerald ore.
Аудит рецептов Fortune вообще не моделирует.

### Арбитраж формы

Девять алмазов продаются отдельно за `9 × 95 = 855`, а diamond block — за 1008.
Один крафт без затрат увеличивает выплату на 153 CR. Для emerald разница
`504 - 9×47 = 81 CR`.

### Готовое лучше сырья

Diamond sword стоит 205 против 280 за два diamond; diamond chestplate 810 против
1120 за восемь diamond. Бесконечной денежной петли нет, но оптимальная стратегия
магазина — не крафтить. Это ломает Minecraft-прогрессию и ценность ресурсов.

### Fallback по rarity/max stack

`PriceManager.java:250-259` назначает неизвестному предмету цену по rarity,
размеру стака и hash-jitter. Полезность, рецепт и доступность не участвуют.
Обычный non-stackable item получает примерно 260–264 CR почти независимо от
смысла.

Четыре задуманные цены случайно закомментированы
(`PriceManager.java:209-210`): `MINECART`, `WHITE_BED`, `WIND_CHARGE`,
`FIRE_CHARGE`. Например, minecart вместо задуманной цены 38 уходит в fallback
около 260 CR.

## P1.8. Существующий price audit даёт ложную уверенность

`tools/priceparse.py:18-20` и `audit_prices.py:17-19` ищут `put(Items..., N)`
регулярным выражением по сырому Java, включая комментарии. Поэтому аудит пишет
«346 позиций», хотя реально компилируются 342 вызова; четыре ошибки выше он не
видит.

Также список 152 рецептов переписан вручную, не берётся из registry/data pack,
и не покрывает:

- Fortune/Silk Touch;
- stonecutting, blasting/smelting, brewing;
- villager trade и loot;
- фермы и производительность в час;
- item components/containers;
- recipes после обновления Minecraft.

Нужен datagen-тест по реальному recipe registry и отдельная симуляция источников
ресурсов/дохода.

## P1.9. GPS создаёт постоянную клиентскую нагрузку

`GpsMapRenderer` при пересэмпле выполняет 160×160 = 25 600 heightmap/block
запросов (`GpsMapRenderer.java:81-90`). Условие `:73-75` пересобирает карту не
только при движении, но и каждые 10 тиков в покое. Это около 51 200 column
samples/сек непрерывно при открытой вкладке, плюс upload полной текстуры.

Нужен chunk-tile cache, инкрементальный сдвиг карты, обновление полосы новых
пикселей и жёсткий per-frame budget.

## P1.10. Биржа показывает валовую продажу как заработок

`StocksManager.sell` увеличивает `STOCKS_EARN` на всю выручку
(`StocksManager.java:377-388`), то есть возврат собственного principal считается
прибылью. Профиль затем суммирует это с зарплатами/продажами как «Заработано».

Нужны average cost basis, realized P&L, unrealized P&L и отдельный cash flow.

# 5. UI/UX и апгрейдер

## 5.1. Почему UI объективно «кривой»

1. Фиксированные размеры: phone 300×240, PvZ 300×212, tower 300×200.
   При scaled height 180 телефон получает `y=(180-240)/2=-30` и обрезается.
2. Нет layout engine, anchors, constraints, scroll containers и responsive
   режима. Все координаты прошиты вручную.
3. `PhoneScreen.java` содержит 1735 строк и восемь приложений в одном классе.
   Изменение одной вкладки легко ломает соседние состояния/input lifecycle.
4. Самодельный `UiKit.TextInput` (`UiKit.java:102-184`) не поддерживает cursor
   movement, selection, Delete/Home/End, Ctrl+A/C/X, Tab navigation, IME и
   горизонтальный scroll до caret.
5. Верхняя панель — восемь одинаково маленьких item-icons без подписей/tooltips
   (`PhoneScreen.java:153-163`).
6. Грубый статический подсчёт нашёл около **312 русских string literal** в
   client-коде (274 уникальных). `en_us.json` не делает эти экраны английскими.
7. Строки часто обрезаются по числу Java chars (`trim`) вместо пиксельной ширины;
   частичный `UiKit.fit` не решает всю систему.
8. Текстуры — программно нарисованные 16×16 примитивы; блок-модели почти все
   `cube_all/cube_column`. Здания — коробки из полных блоков с плоской крышей,
   без дверей, дорог, biome palette и нормального окружения.

### Предлагаемая UI-архитектура

- Отдельный Screen/ViewModel на приложение вместо одного `PhoneScreen`.
- Для инвентарных операций — `ScreenHandler` и настоящие slots/ghost slots.
- Стандартный `TextFieldWidget`, `ButtonWidget`, narration/focus navigation.
- Responsive layout с минимальным compact-mode и внутренним scrolling.
- Общая design token система: spacing 4/8/12, row heights, typography, semantic
  colors, disabled/error/loading states.
- Все строки через translation keys; сервер отправляет item Text/component, а не
  результат `getName().getString()` на языке сервера.
- Tooltip у каждой иконки и предмета; item tooltip должен показывать components.
- Визуальные regression screenshots на 320×180, 426×240, 640×360 и нескольких
  GUI scales.

## 5.2. Апгрейдер: конкретные проблемы

### Математика не соответствует обещанию

README обещает: «приз вдвое дороже → ровно 50%». Код считает
`stakeSell / targetBuy × RTP` (`CasinoManager.java:86-90`). При RTP 90% это 45%,
а не 50%.

Даже diamond → diamond даёт только `95/140×0.9 ≈ 61.1%`, потому что ставка
оценивается по sell, цель по buy. Для пользователя это выглядит как скрытое
двойное наказание, даже если формула формально показана мелким текстом.

### Результат раскрывается до рулетки

`CasinoManager.spin` сразу очищает ставку, бросает RNG, выдаёт предмет, чат и
звук (`CasinoManager.java:191-220`). Затем immediate screen sync запускает
клиентскую анимацию (`PhoneScreen.java:483-505`) длительностью ~3.1 с. После неё
клиент играет ещё один звук (`:886-890`).

Игрок узнаёт исход по инвентарю/чату/первому звуку до остановки стрелки.
Рулетка не создаёт suspense и ощущается фальшивой.

### Остальные UX-дефекты

- Источник ставки обрезан первыми 12 видами инвентаря
  (`ServerActions.java:882-891`), без поиска/пейджинга/сортировки.
- Из ставки нельзя убрать один вид/часть — только очистить всё.
- Нет предупреждения, что стоимость выше 95%-cap полностью сгорит без роста
  шанса.
- Нет возврата excess stake.
- Нет истории ставок, понятного breakdown стоимости и ожидаемой потери.
- Выбор цели хранится только на клиенте и сбрасывается при переоткрытии, а escrow
  ставки остаётся на сервере.
- Cosmetic angle строится от глобального последовательного spin id; никакой
  проверяемой честности/commit-reveal нет.

### Предлагаемый новый flow

1. **Stake tray** из точных ItemStack slots; +/- количество, remove one, clear.
2. **Target** с поиском, категориями, favorites и сравнением market/shop value.
3. Большая строка: stake value, target value, RTP, chance, cap, excess, EV.
4. Нельзя отправить excess молча: вернуть лишнее или запросить подтверждение.
5. Сервер создаёт pending spin и commit; клиент анимирует; reveal/выдача/звук
   происходят в конце, а не до него.
6. История последних спинов и server-configurable fairness policy.
7. Полная сохранность Data Components и защита от disconnect/restart между
   commit и reveal.

# 6. P2 — архитектура и поддерживаемость

## P2.1. Монолиты и сырые magic-key NBT

Крупнейшие классы:

- `PhoneScreen` — 1735 строк;
- `ServerActions` — 1045;
- `JobManager` — 938;
- `VillageManager` — 785.

Данные передаются как общий `NbtCompound` с короткими ключами (`bld`, `bmask`,
`tlv`, `sv`, `tv`, `c`, `p`, `d`). Нет typed payloads, schema version и явных
миграций. Любая опечатка превращается в тихий default 0/empty.

Нужны codec-backed records по доменам, versioned state и migration tests.

## P2.2. Исключения скрывают диагностику

Есть восемь `catch (Throwable)`. Ключевые handlers логируют только
`t.toString()`, без stack trace (`ServerActions.java:177-179`,
`VillageManager.java:391-394`). `Error`/linkage/OOM ловить как обычную ошибку
действия нельзя. Для проблемы «здания не появились» такой лог недостаточен.

## P2.3. CI не тестирует заявленные инварианты

`.github/workflows/build.yml` вызывает только `gradle build`. Python tools не
подключены, Java tests отсутствуют, GameTests отсутствуют. Поэтому зелёный CI
подтверждает компиляцию/remap, но не:

- генерацию деревни;
- загрузку NBT entities;
- доставку/claim;
- сохранение components;
- packet authorization;
- экономику;
- UI на разных resolution.

## P2.4. Документация расходится с кодом

Примеры:

- README: chips `x2/x4/x8/30/50/70%`; код: `10/25/50/75/90%`.
- README: «вдвое дороже → 50%»; код с RTP даёт 45%.
- `DESIGN.md`: Loom 1.17.15 / Gradle 8.14.3; properties/workflow используют
  Loom 1.17.19 / Gradle 9.5.1.
- Tutorial говорит о 12 achievements, код/README — 20.
- README одновременно пишет примерно 350 и примерно 170 цен.
- Документация утверждает reload всех настроек, но static finals не меняются.

## P2.5. Сборка невоспроизводима локально

В репозитории нет `gradlew` и `gradle-wrapper.jar`; wrapper properties указывает
8.14.3, CI — 9.5.1, README требует системный 9.5+. Ожидаемый стандарт проекта —
полный Gradle Wrapper и одна закреплённая toolchain/version matrix.

## P2.6. Сервер заранее локализует item names в String

Много мест вызывает `ItemStack.getName().getString()` и кладёт строку в NBT.
Так теряется translatable Text и язык конкретного клиента. Нужен registry id или
serialized Text; локализацию должен делать клиент.

## P2.7. README/REVIEW создают неверную оценку зрелости

`REVIEW.md` заканчивается «открытых находок нет», CHANGELOG называет сборку
production и ссылается на зелёный CI. Это опаснее обычного отсутствия документа:
он формирует ложную уверенность, хотя runtime/game tests отсутствуют.

# 7. Что в проекте уже полезно

Чтобы не выбросить всё без разбора:

- Основные денежные действия в большинстве случаев решаются на сервере.
- PersistentState и codec ItemStack уже используются в orders/части market;
  этот подход можно распространить на escrow.
- Есть попытка вынести параметры в config и price file.
- Есть русская и английская таблицы translation keys для сообщений.
- Python-аудиты — полезная заготовка, если подключить их к CI и заменить regex/
  ручные списки на реальные данные игры.
- Разделение Money/Orders/Market/Stocks/Stats как доменов можно сохранить,
  переписав контракты и typed state.
